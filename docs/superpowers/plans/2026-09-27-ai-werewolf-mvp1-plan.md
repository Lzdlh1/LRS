## 8.1 M1 实施记录（2026-09-27）

**结果**：154 个测试用例全部通过，`tsc --noEmit` 干净，随机对局 40 局全部正常结束且**零非法 Action**。

**实施中对契约做的调整**（原设计未覆盖，编码时才发现）：

| 调整 | 原因 |
|---|---|
| `chief_withdraw` 增加 `withdraw: boolean` | 退水环节需要同时表达「退水」与「不退水」，只有一个方向的 Action 无法让 AI 作出完整选择 |
| 新增 Action `chief_transfer`（target 可为 null） | 警长死亡后需要决定移交警徽还是撕毁；null 表示撕毁 |
| PHASES 新增 `CHIEF_TRANSFER` | 警徽去向必须在遗言之前处理 |

**相对设计文档的简化**（已知差异，后续按需补）：

| 简化 | 现状 | 影响 |
|---|---|---|
| 发言起点 | 固定为「警长下一位开始，顺时针，警长最后」；无警长则从最小座位号开始 | 设计文档写的是「起点由警长指定」。少了一个博弈点，但不影响胜负判定 |
| 第二天换手 | 未实现 | 发言顺序每天相同 |
| 狼队刀人 | 由座位号最小的存活狼代表提交 | 狼队内部协商属于 agent-host 的职责，M3 实现 |
| 黄金回放 fixture | 改为「同种子重放结果完全一致」+ 手写黄金用例 | 生成 fixture 的独立脚本在 Node 类型剥离下跨包解析复杂；确定性与手写断言覆盖了同样的回归需求 |

**已实测覆盖的边界情况**：同守同救、女巫自救限制、猎人被毒死不能开枪、守卫连守排除、平票 PK 再平票、警长 1.5 票、首夜死者照常参与竞选、狼刀在先。

## 8.2 M2 实施记录（2026-09-27）

**结果**：184 个测试用例全部通过；已在真实浏览器里实测——连接、点击提交行动、连续代打、视角切换、打完一整局（狼人胜）全部正常。

**技术选型调整**：

| 原计划 | 实际 | 原因 |
|---|---|---|
| Fastify | 原生 `node:http` | 当前只需要健康检查 + WS 升级，引入框架没有收益；将来需要路由/插件再换 |
| better-sqlite3 | Node 24 内置 `node:sqlite` | 免去原生编译，Windows 上省掉一大类环境问题 |
| tsc 构建产物 | 无构建步骤 | Node 24 原生剥离类型，直接 `node src/index.ts` 即可跑 TS |
| 前端 Pinia | 一个 composable | 全局只有一个 store，`ref` + 函数足够，不引入额外抽象 |
| 默认视角 = 玩家视角 | 默认上帝视角 | M2 用于人工验证规则，看全场更方便；**M4 会改回玩家视角** |

**开发中发现并修掉的两个真问题**：

1. **vitest 里 `ws` 客户端连不上服务端**（独立 Node 进程正常）。端到端测试改用 Node 内置的 WHATWG `WebSocket` —— 反而更贴近前端真实路径，测试从 20 秒超时变成 81 毫秒通过。
2. **小视口下圆桌把底部操作区顶出屏幕**（浏览器实测时按钮点不到）。已改为：滚动收在中间区域内部 + 圆桌按视口高度分档等比缩放，保证操作区在任何高度下都可见可点。

**这一里程碑实际交付的可玩路径**：`npm run dev:server` + `npm run dev:web`，浏览器打开 http://localhost:5173 —— 一个人可以扮演全部 9 个座位从头打到尾，并用「代打」按钮快速跑完。

## 8.3 M3 实施记录（2026-09-27）

**结果**：214 个测试用例全部通过。用假大脑（MockProvider）验证了完整链路：**8 个 AI 自动行动，真人只在自己回合点一下，一整局能自动跑完，全程零非法行动**。真实模型效果待 Key 到位后验证。

**开发中发现并补上的引擎缺口**：

- 引擎从没发出过 `action_requested` 事件 —— 契约里定义了、设计文档也写了，但状态机只是把待办塞进 `state.pending` 就完事。已补发（私密可见），这样整局事件日志是自包含的，复盘和 AI 记忆都靠它。

**为共用而做的结构调整**：

- 「把引擎选项摊平成可提交动作」的逻辑从 web 移到了 core-engine。前端按钮和 AI 决策必须用同一份「现在能做什么」，两边各写一套迟早在某个边界情况下漂移。

**相对设计文档的简化**：

| 简化 | 现状 | 影响 |
|---|---|---|
| 摘要层（M3） | 用**确定性压缩**：从事实层直接生成每日要点，不额外调模型 | 零成本、零幻觉；代价是不会「把一段发言提炼成一句话」，只保留结构化事实 |
| 狼队协商 | 由座位号最小的存活狼代表决策，队友的当前判断会出现在它的提示词里 | 有信息对齐，但没有多轮讨论；狼队配合深度不如真人 |
| 无 Key 时的行为 | AI 提交兜底动作，游戏仍能完整跑完 | 方便本地调试；日志会明确警告「未配置任何可用的 LLM Key」 |

**验证方式**：单元测试 + 真实 WebSocket 端到端（真假大脑两种）+ 服务器实际启动（健康检查返回 `ai:false` 时说明未配 Key）。

## 8.4 M4-1 实施记录：流式输出（2026-09-27）

**结果**：用真实 DeepSeek 在浏览器里实测通过 —— 发言是逐字长出来的，不是一次性蹦出来。

**改动链路**：

```
Agent.composeSpeech  →  router.stream() 每来一个增量就调 onSpeechDelta
AgentHost            →  按座位号转发给房间
GameRoom             →  广播 { type: 'stream', seat, delta }
前端 useGameSocket   →  累积成 streaming 状态
EventLog             →  日志末尾一行带光标的「直播行」
RoundTable           →  中心显示「N 号发言中」+ 说话座位呼吸高亮
```

**几个刻意的取舍**：

| 取舍 | 原因 |
|---|---|
| 流式片段仍以 `spoke` 事件为最终依据 | 流是"草稿"，事件才是"说了什么"。落地时用事件里的干净文本替换，避免两套真相 |
| 发言流不做视角过滤 | 发言本来就是公开信息（大家都听得到）。真正的信息隔离仍由事件裁剪负责 |
| 额外发一条 `stream-done` | 不然一旦这次行动被丢弃（局面已变），前端光标会一直闪 |
| 显示层压平换行 | 模型输出里有 `\n\n`，而最终落地文本会把空白压成单空格。不统一的话，正式发言落地那一刻看起来像「文字被改了」 |

**实测确认**：抓到了 `4 号发言中` / `6 号发言中` 两段实时增量；`speakingSeat: "6"` 证明座位高亮生效；`思考中`（AI）与 `等待`（真人）区分正确；浏览器控制台零错误。

**测试**：215 个用例全绿（新增 1 个流式端到端用例：断言流式拼接结果与最终 `spoke` 文本完全一致）。

## 8.5 M4-2 实施记录：并行预思考（2026-09-27）

**先纠正一个原定目标。** 设计文档里 M4-2 的验收标准是「用户发言结束后，下一个 AI 几乎立刻开口」，这条**字面上做不到**：下一个 AI 的判断必须建立在真人刚说的那句话之上，提前算就等于让它凭空猜。

所以实际做的是**能真实并行、且语义正确**的那部分 —— 把「规则上本来就是同时发生」的阶段一次性问完：

| 阶段 | 能否预思考 | 依据 |
|---|---|---|
| 上警、退水 | ✅ 可以 | 每个人决定时并不知道别人怎么选，待办彼此独立 |
| 发言 | ❌ 不行 | 后发言的人必须听到前面说了什么 |
| 放逐投票 | ⚠️ 暂时保持串行 | 依次投票、票型公开，后面的看得到前面的票 |

规则知识留在引擎里：新增 `concurrentBatch(state)` 返回「当前阶段剩下的待办能否一次问完」，返回 null 表示只能一个一个来。房间不猜规则，只负责按它发起并行。

**实测数据**（一局真实 DeepSeek 对局）：

| 指标 | 数值 |
|---|---|
| 一局耗时 | **185.7 秒**（105 次调用） |
| 全部调用延迟的串行累加 | 301.4 秒 |
| **被并行隐藏掉的时间** | **约 115 秒（38%）** |
| `chief_signup` 实际发起跨度 | 12.0s（串行会是 58.0s） |
| `reflection` 每批 8 次发起跨度 | 2.4s（串行会是 24s） |
| `speak` 发起跨度 | 169.6s —— **严格串行，符合规则** |

**顺手修掉两个真 bug**（都是这轮测试逼出来的）：

1. **AI 上一阶段的行动会被误当成当前阶段的行动提交。** `runAiTurn` 原先只比对座位号 —— 但同一个座位可能在下一个阶段又被点到，于是夜里的「刀人」会被当成「上警」提交。现在改成用完整的合法性校验（这个行动是否仍在当前待办的可选项里）。
2. **`isStillAllowed` 对发言待办永远返回 false** —— 因为 `choicesFor` 不给「发言」生成按钮。上面那个修复一上线就把 AI 发言全丢了，对局直接卡死。发言阶段改为只校验「是不是该座位在发言」。

这两条也说明：**「只比座位号」这种看似够用的校验，在多阶段状态机里是不够的。**

**另外把「模型调用完成」日志从 debug 提到 info** —— 每次调用的延迟与 token 是调优和成本看板的核心数据，之前被默认级别丢掉了，导致根本无法按任务分析延迟。

**测试**：217 个用例全绿（新增 2 个：一个断言「真人还没动手，8 个 AI 的决策已全部发出且发起时间跨度 < 200ms」，一个断言「发言阶段不会有人被提前预跑」）。修复前该用例 6 次里失败 3 次，修复后 6/6 稳定。

**关于「继续压缩耗时」的决定：不做。**

延迟在这里**是节奏，不是缺陷** —— 真正的狼人杀对局本来就不短，AI 太快反而让人跟不上、失去在脑子里盘逻辑的时间。所以：

- 投票保持「依次投票」（后面的看得到已亮出的票型，更接近线上 App 的体感）
- 投票保持 strong 档，不为了省时间降级到便宜模型
- 已实现的并行**只用在「规则上本来就是同时发生」的阶段**，不为了提速去改玩法

> 后续若有人想「优化」这块（把投票并行化、给发言加预取），请先回来看这条。

## 8.6 M4-3 实施记录：视角切换（2026-09-27）

**默认视角改回玩家视角**（1 号），上帝视角变成右上角的调试开关。切换本身 M2 就能用，这一轮真正的工作是**修掉玩家视角下的两处信息泄漏**：

| 泄漏 | 后果 | 修法 |
|---|---|---|
| 夜间下发 `pending.seat` | 夜间顺序是固定且公开的，「现在轮到 8 号」**等于直接告诉所有人 8 号是守卫** | 新增 `masked`：旁观者在夜间既看不到「轮到谁」，也看不到阶段细节 |
| 死讯公布前下发 `alive` / `deathCause` | 变体 A 下首夜死讯在**上警之后**才公布，而引擎在结算夜晚时就写入了死亡状态 —— 期间玩家的屏幕上会提前看到谁死了、死于狼刀还是毒 | 死讯未公布前对外一律算「在场」，与引擎自己的 `onBoardSeats` 同一口径 |

第二处特别值得一提：它依赖「变体 A 让首夜死者先参与上警」这个规则选择 —— 如果当初选了变体 B（先公布死讯再竞选），这个泄漏就不存在。**规则一变，信息边界也得跟着变。**

**实测（浏览器，真实对局）**：

| 检查项 | 结果 |
|---|---|
| 默认视角 | `我的视角 · 1 号`，座位 1 标记为「我」 |
| 玩家视角下别人的身份 | 不显示（`玩家2`、`玩家3`… 无身份） |
| 自己的身份与狼队友 | 正常显示（`玩家1 · 狼人`、`你的狼队友：2 号、5 号`） |
| 夜间旁观 | 阶段只显示「夜晚」，中央「天黑请闭眼」，**不点亮任何座位**，无行动选项 |
| 切到上帝视角 | 阶段细节 + 行动座位 + 药水 + 全部 9 个身份立刻可见 |

**顺带**：女巫的药水数量做成顶部状态条（`🧪 解药 0 · 毒药 1`），这也是「夜间面板随视角变化」的一部分。

**测试**：219 个用例全绿。新增 2 个锁死上面两处边界的用例，并把原来那条「非行动者能看到座位号」的用例改成只在白天成立 —— 夜间保密是有意为之，不是回归。
