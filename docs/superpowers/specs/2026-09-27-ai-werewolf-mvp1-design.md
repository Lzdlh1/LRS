# AI 狼人杀 · MVP1 设计文档

- 日期：2026-09-27
- 范围：纯文字 · 单人局（1 真人 + 8 AI）· 9 人预女猎守
- 目标产物：能在本地完整打完一局、AI 表现像人的可运行系统

---

## 1. 背景与目标

做一个「AI 陪我玩狼人杀」的应用。最终形态包含五个子系统：游戏引擎、AI 智能体、交互界面、语音模块、多人联网。它们不适合一次性做完，因此拆成独立的「设计 → 计划 → 实现」循环。

**MVP1 只做其中三个**：游戏引擎 + AI 智能体 + 交互界面（纯文字）。

**MVP1 的目标**：一个人坐在电脑前，打开浏览器就能和 8 个有性格、有记忆、会推理的 AI 打一局完整的 9 人预女猎守，并且打完能复盘。

### 1.1 明确不做（MVP1 范围外）

| 不做 | 原因 |
|---|---|
| 语音 ASR / TTS | 会与 AI 调优互相拖慢，且出问题时难以定位是 AI 笨还是语音糊 |
| 多人联网、房间系统 | 需要并发/一致性与部署，MVP 阶段过度设计 |
| 跨局长期记忆 | 需要向量检索与长期存储，不可控性高 |
| AI 难度分级 | 尚未知 AI 实际会偏笨还是偏精，此时定档位是拍脑袋 |
| 移动端适配 | 先保证 PC 浏览器体验 |
| 数据库选型升级（PostgreSQL/Redis） | 单机场景 SQLite 足够 |

### 1.2 MVP1 之后的三段式演进

架构设计已为后续预留，**不需要重写**：

1. **现在** — 本地 Web：Node 服务跑引擎 + AI，浏览器是界面
2. **下一步** — 用 Tauri 套壳成桌面 App（前端代码几乎不动）
3. **再下一步** — 把同一个 Node 服务挪到云上 + 加房间管理，直接支持多人

## 3. 架构与模块边界

```
        ┌──────────────────────────────────────┐
        │  web-ui · 浏览器                      │
        │  Vue3 · 圆桌 / 日志 / 操作区           │
        └───────────────┬──────────────────────┘
                        │ WebSocket（只传「你该看到的事件」）
        ┌───────────────▼──────────────────────┐
        │  session-service · 会话服务           │
        │  生命周期 │ 信息裁剪 │ 调度 │ 流式转发 │
        └───────┬───────────────────┬──────────┘
                │ Action            │ Event
        ┌───────▼────────┐  ┌───────▼──────────┐
        │  core-engine   │  │  agent-host      │
        │  纯逻辑状态机   │  │  人设/记忆/决策    │
        └────────────────┘  └───────┬──────────┘
                                    │
                          ┌─────────▼──────────┐
                          │  llm-router        │
                          │  分级 / 并发 / 计费  │
                          └─────────┬──────────┘
                                    ↓
                  DeepSeek / OpenAI / Claude / Ollama
                                    ↕
                          ┌────────────────────┐
                          │  SQLite            │
                          └────────────────────┘
```

### 3.1 模块职责与边界

| 模块 | 做什么 | 边界（不做什么） |
|---|---|---|
| **core-engine** | 阶段状态机、Action 合法性校验、死亡结算、胜负判定、产出事件流 | 不发网络请求、不读写文件、不调 LLM、不知道「AI」存在、不处理超时、不做信息裁剪 |
| **agent-host** | 订阅事件流 → 更新记忆 → 调 LLM → 产出 Action，实现 8 个 AI 玩家 | 不直接改引擎状态、不直接连前端 |
| **llm-router** | 唯一知道 API Key / 模型名 / 计费的地方；任务分级、并发控制、重试降级、用量统计 | 不懂游戏规则 |
| **session-service** | 唯一对外入口；对局生命周期、信息裁剪、行动调度与超时、流式转发、断线补发 | 不含游戏规则判断 |
| **web-ui** | 纯展示 + 输入 | 不含任何规则判断，永远拿不到不该看到的信息 |
| **SQLite** | 对局存档、全量事件日志、人设、用量 | **不存 API Key** |

### 3.2 三个核心设计原则

1. **引擎不知道「AI」存在。** 它只认「有个玩家要行动，给我一个 Action」。好处有二：引擎能用纯单元测试跑完整局；真人客户端与 AI 是同一个接口 —— 这就是多人模式的接口预留。

2. **信息裁剪在服务端，不在前端。** 引擎只标记事件的 `visibility`，真正的过滤由 session-service 执行。这一条同时解决三件事：视角可切换、前端改代码也偷看不到底牌、多人模式下每个客户端天然只收到自己该看的。

3. **事件溯源（Event Sourcing）。** 引擎输出一串不可变事件，日志、复盘、AI 记忆全部由这串事件派生。复盘功能因此几乎是白送的 —— 按 `seq` 回放即可。

## 4. core-engine 设计

### 4.1 板子配置

**9 人预女猎守**：3 狼人 + 预言家 + 女巫 + 猎人 + 守卫 + 2 平民 = 9

### 4.2 阶段状态机

```
开局：发牌定座位号（1-9）→ 确认身份（私密下发）

【第 1 夜】顺序固定
  ① 守卫守护 → ② 狼人刀人 → ③ 女巫救/毒 → ④ 预言家验人

【第 1 天】
  ① 警长竞选
     上警报 → 竞选发言（号序）→ 退水 → 警下投票
     → 平票则 PK 发言 → 再投（仅一轮）→ 警长产生
     （再次平票则警徽流失，本局无警长）
  ② 公布死讯 → 死者遗言（如适用）→ 猎人开枪（可选）
  ③ 依次发言（起点由警长指定，含警徽流）→ 全员投票
     → 平票则 PK 发言 → 再投 → 遗言 + 猎人开枪
  ④ 判定胜负

【第 N 夜·可循环，N ≥ 2】顺序固定
  ① 守卫守护 → ② 狼人刀人 → ③ 女巫救/毒 → ④ 预言家验人

【第 N 天·可循环】
  ① 公布死讯 → 遗言（如适用）→ 猎人开枪（可选）
  ② 依次发言 → 全员投票 → 平票 PK → 遗言 + 猎人开枪
  ③ 判定胜负

【结算】
  屠边判定 / 好人胜 → 亮底牌 + 生成复盘数据
```

> **第一天顺序说明**：警长竞选排在公布死讯**之前**（变体 A，依据《烂柯游艺社狼人杀法典》与搜狐规则入门）。因此**首夜死者此时尚不知情，会照常参与上警与警长投票**，竞选结束后才被宣布死亡。该顺序走配置开关，默认 A。

### 4.3 规则参数（可配置，含默认值）

引擎的规则细节全部走配置，不硬编码，便于以后换板子或调规则变体。

| 参数 | 默认值 |
|---|---|
| 守卫守护 | 每晚守一人；不可连续两晚守同一人；可以守自己 |
| 女巫用药 | 解药 1 瓶 + 毒药 1 瓶；**一晚只能用一瓶**；**不能自救** |
| 同守同救 | 守卫守的人同时被女巫救 → **该玩家死亡**（奶穿） |
| 猎人开枪 | 被狼刀或被投票出局可开枪；**被女巫毒死不能开枪** |
| 警长 | 警长票算 **1.5 票**；竞选再次平票则**警徽流失**；警长死亡时可移交警徽或撕毁 |
| 遗言 | 首夜死亡者有遗言；白天被投出局者有遗言；其余夜间死亡者无遗言 |
| 平票处理 | PK 发言后重投；再次平票则本轮无人出局 |
| 第一天顺序 | **变体 A**：天亮 → 警长竞选 → 公布死讯 → 发言 → 投票；**首夜死者照常参与竞选** |
| 狼刀在先 | 若狼人当夜达成胜利条件（且女巫未救），直接判狼胜 —— 后手的毒杀 / 猎人开枪不改变结果 |
| 胜负 | 屠边：狼杀光 4 神 或 杀光 2 民 → 狼胜；狼全灭 → 好人胜 |

### 4.4 Action 契约（外部 → 引擎）

```ts
type Action =
  // 夜晚
  | { kind: 'guard_protect';  actor: SeatId; target: SeatId }
  | { kind: 'wolf_kill';      actor: SeatId; target: SeatId }   // 狼队共识，以发起狼为代表
  | { kind: 'witch_act';      actor: SeatId; use: 'save' | 'poison' | 'pass'; target?: SeatId }
  | { kind: 'seer_check';     actor: SeatId; target: SeatId }
  // 警长竞选
  | { kind: 'chief_signup';   actor: SeatId; join: boolean }
  | { kind: 'chief_withdraw'; actor: SeatId }
  // 白天
  | { kind: 'speak';          actor: SeatId; text: string }
  | { kind: 'vote';           actor: SeatId; target: SeatId | 'abstain' }
  | { kind: 'hunter_shoot';   actor: SeatId; target: SeatId | null }
```

### 4.5 Event 契约（引擎 → 外部）

```ts
type Visibility =
  | { scope: 'public' }                 // 所有人可见
  | { scope: 'seats'; seats: SeatId[] }  // 只有这些人可见

type GameEvent = {
  seq: number;        // 单调递增 —— 事件溯源主键
  day: number;
  phase: Phase;
  visibility: Visibility;
  payload: EventPayload;
}
```

主要 payload：

| payload | visibility | 说明 |
|---|---|---|
| `game_started` | public | 座位与公开信息 |
| `role_assigned` | seats[本人] | 身份下发 |
| `wolf_teammates` | seats[各狼] | 狼队友 |
| `phase_changed` | public | 阶段推进 |
| `action_requested` | seats[行动者] | 含 `options` 与 `deadline` |
| `spoke` | public | 发言记录（**不改变游戏状态**） |
| `seer_result` | seats[预言家] | 验人结果 |
| `witch_night_info` | seats[女巫] | 今夜谁被刀 |
| `died` | public | `cause: wolf / poison / vote / gun` |
| `chief_elected` | public | 警长产生 |
| `vote_tally` | public | 票型 |
| `game_over` | public | 胜方 + 亮底牌 |

### 4.6 三个关键设计点

1. **`action_requested` 里带 `options`** —— 引擎直接给出「你现在合法能做什么」（守卫不能连守、女巫没药了就没这个选项、猎人被毒死不能开枪）。AI 只需在合法选项里挑，**从根上杜绝 AI 产生非法行动**。

2. **发言不改变游戏状态** —— `speak` 只被记录进事件流。AI 说错话不会把引擎搞崩，复盘时又能完整还原。

3. **私密事件是一等公民** —— 引擎只标记 `visibility`，裁剪由 session-service 执行。「上帝视角」的实现就是把 visibility 过滤器关掉。

### 4.7 超时不属于引擎

引擎只发 `action_requested(deadline)`，不持有定时器、没有真实时间概念，保持纯函数性 —— 单元测试不需要假时钟。真正执行「超时 → 提交默认 Action」的是 session-service。

### 4.8 必须覆盖的边界测试

同守同救 × 女巫自救限制 × 猎人被毒死不能开枪 × 守卫连守是否合法 × 平票 PK 后再次平票 × 警长被刀后警徽转移 × 狼全灭与屠边同时发生时的胜负判定 × 首夜死亡者是否有遗言 × **首夜死者照常参与警长竞选与投票** × 竞选再次平票导致警徽流失 × **狼刀在先**（狼当夜达成胜利条件时，后手毒杀/开枪无效）

## 5. agent-host 设计

### 5.1 记忆三层结构

核心思路：**把「客观事实」与「AI 的主观推断」彻底分开。**

| 记忆层 | 名称 | 来源 | 特点 |
|---|---|---|---|
| **M1** | 事实层 Facts | 引擎事件流直接投影，**零 LLM 参与** | 存活名单、票型、宣称、死亡。AI 永远不会「记错谁投了谁」 |
| **M2** | 信念层 Belief State | LLM 产出，结构化 | 对每个座位 `{ 身份猜测, 置信度 0-1, 一句话理由 }`，另含「今天要推谁」的立场、狼队共识、`mood` |
| **M3** | 摘要层 Narrative | LLM 压缩，每轮更新一次 | 把长对话压成一句话，解决上下文爆炸 |

### 5.2 上下文预算策略

- M1 / M2 / M3 **全量保留**（结构化后很紧凑）
- 发言原文：**只保留最近一轮**，更早的只留摘要
- 目标：把单次调用规模控制在可预测范围内，不随局数增长而爆炸

### 5.3 提示词四层拼装

| 提示词层 | 内容 | 更新频率 |
|---|---|---|
| **P1 人设层** | 性格、说话风格、思维习惯、口头禅 | 永久不变 |
| **P2 规则与身份层** | 板子、我的身份与技能、胜利条件、狼队友 | 每局开始 |
| **P3 记忆与局面层** | M1 事实 + M2 信念 + M3 摘要 + 最近一轮发言原文 | 每次调用动态拼装 |
| **P4 任务层** | 「现在做什么」+ 输出格式约束 | 每次调用 |

### 5.4 先想，后说（最重要的一条）

**拆成两次独立调用**，而不是让模型「边想边说」。

- **调用 A · 决策**（强模型）
  输入 P1+P2+P3 + 「给出你的行动决策」→ 输出结构化 JSON：
  ```json
  {
    "action": { "kind": "speak_stance", "push": 5 },
    "reasoning": "5 号无理由站边我，是狼在给我抬轿；我先立威",
    "belief_update": { "5": 0.82 }
  }
  ```
- **调用 B · 发言**（便宜模型，流式）
  输入 P1+P3 + 决策结论 + 「用你的口吻说出来」→ 自然语言

**为什么必须拆开**：若让模型边想边说，它会一边组织语言一边推理，很容易出现「前面说 5 号是狼，后面又说 5 号像好人」的自相矛盾。拆开后，决策调用在一个清晰框架里推理，发言调用只负责把已定好的结论演绎成人话。

**顺带省钱**：决策用强模型保质量，发言用便宜模型保成本。

### 5.5 反思机制

投票结果公布后触发一次反思调用（便宜模型）：

- 输入：我的预测 vs 实际发生的
- 输出：更新信念层 + 一句「教训」

示例输出：

> 「我押 5 号是狼，结果票出去的是 8 号，而且 5 号投了 8 号 —— 那 5 号可能反而是好人。5 号置信度 0.82 → 0.45。教训：站边太快的人未必是狼，也可能是好人被带了节奏。」

### 5.6 情绪与策略变化

不靠提示词硬演，而是**推理结果驱动**：

- 信念层持有一个 `mood` 字段（焦虑 / 自信 / 迷茫 / 亢奋）
- 由反思调用更新（如连续两次押错 → 焦虑）
- 再注入回 P1 人设层影响措辞（变得急躁、更容易跟风）

### 5.7 模型路由表

| 任务 | 档位 | 理由 |
|---|---|---|
| 投票决策 | strong | 直接决定胜负 |
| 狼人刀人 | strong | 需要团队策略 |
| 警长竞选 / 退水 | strong | 高强度博弈 |
| 预言家验人 | strong | 影响后续全部推理 |
| 女巫救 / 毒 | strong | 一次决策定生死 |
| 守卫守护 | cheap | 信息最少，接近随机 |
| 发言生成 | cheap | 一局 40~60 次，只需演绎不需推理 |
| 发言摘要压缩 | cheap | 纯压缩 |
| 反思 | cheap | 短输出 |

预估单局：strong 调用 15~20 次，cheap 调用 50+ 次。

### 5.8 并行与延迟

**并行约束（有坑）**：

- 夜晚**不能全并行**：守卫 ∥ 狼人 ∥ 预言家 可同时跑，但**女巫必须等狼人出刀结果**
- 白天发言**必须串行** —— 后面的人要听到前面的人说了什么，这是狼人杀的本质
- 投票**可以并行** —— 暗票本来就是同时投

**延迟缓解手段**：

1. **预思考**（关键优化）—— 用户发言时，其他 AI 并行预生成「如果轮到我我会说什么」的草稿；用户发完，下一个 AI 的草稿基本已就绪
2. 流式输出 + 打字机效果
3. 用户可「跳过」当前 AI 发言

### 5.9 人设

- 内置 9 个手写人设（搬硬型、冲动型、稳健型、插科打诨型…），每局随机分配
- 提供自定义人设编辑入口，存入 `ai_profiles`

## 6. llm-router 设计

- **Provider 抽象**：统一接口，适配 DeepSeek / OpenAI / Claude / Ollama
- **任务分级路由**：上层只说 `tier: 'cheap' | 'strong'`，由路由层决定具体 provider + model
- **并发控制**：白天投票可并行，需带限流，避免触发供应商速率限制
- **重试 / 超时 / 降级**：失败自动回落（如 strong 超时 → 降级 cheap 或使用保守默认 Action）
- **输出校验**：用 Zod 校验 LLM 返回的 JSON；校验失败则重试一次，再失败则退化为默认 Action 并记日志
- **用量统计**：每次调用记录 provider / model / tier / tokens / cost / 耗时，写入 `llm_usage`

## 7. session-service 设计

### 7.1 四条职责

| 职责 | 内容 |
|---|---|
| 对局生命周期 | 建房、发牌、开局、结束、生成复盘 |
| 信息裁剪与广播 | 按 `visibility` 过滤、视角开关、断线按 `seq` 补发 |
| 行动调度与超时 | 问该问的人、计时、超时提交默认 Action |
| 流式转发 | 把 LLM 的流式输出边收边推给前端 |

### 7.2 一次「轮到你发言」的事件流转

```
session-service → 引擎说「轮到 3 号发言」→ 问 agent-host「3 号该说什么？」
agent-host     → 取记忆 → 决策调用(strong) → 写回信念层 → 发言调用(cheap,流式) → 产出 speak Action
session-service → 把 speak Action 交给 core-engine
core-engine    → 校验合法性 → 产生 spoke 事件（public）
session-service → 按 visibility 裁剪后同时：
                 · 推给 web-ui（流式打字机显示）
                 · 推给其他 8 个 agent-host（更新记忆）
                 · 写入 SQLite 事件表
```

若事件是 `visibility: seats[3]`（如验人结果），则**只推给 3 号** —— 其他人连这条事件存在都不知道。

### 7.3 真人玩家的 Action 从哪来

同一个入口：`web-ui → session-service → core-engine`。区别只在于 AI 的 Action 由 agent-host 生成、真人的 Action 由 web-ui 提交。引擎完全不关心这个差别 —— 这正是多人模式的接口预留。

## 8. web-ui 设计

### 8.1 主界面布局（圆桌环绕式）

```
┌────────────────────────────────────────────────────┐
```

**座位状态**：存活 / 发言中（发光）/ 出局（灰 + ✕）/ 你（绿边）

## 10. 日志与安全

### 10.1 日志结构

```
logs/2026-09-27/
  engine.log   阶段流转 / Action / 事件（JSONL，按 seq）
  agent.log    每个 AI 的 reasoning 与发言（排查「AI 为什么这么想」的关键）
  llm.log      provider / model / tier / 延迟 / tokens / 重试次数
  ws.log       连接 / 订阅 / 补发
  error.log    异常栈
```

全部 JSONL 结构化，便于直接 grep。

### 10.2 防泄密机制

1. **统一脱敏器**：匹配 `sk-*` / `Bearer *` / `api_key` 等模式 → 一律打码
2. **prompt 全文默认不落盘**，仅显式加 `--debug-prompts` 时才写；写了也只保留 7 天并自动清理
3. **日志目录进 `.gitignore`**，`.superpowers/` 同理
4. **启动时自检**：扫描日志目录，发现疑似 Key 立刻告警
5. API Key 走环境变量 / 本地配置文件，**禁止硬编码、禁止进 git**

## 14. 风险与应对

| 风险 | 应对 |
|---|---|
| AI 推理质量差、逻辑混乱 | 先想后说拆分；反思机制；关键决策上强模型 |
| 多 AI 串行调用慢 | 预思考 + 流式输出 + 可跳过 |
| AI 产生非法 Action | `action_requested` 携带合法 `options`，AI 只在合法集内选；llm-router 侧 Zod 校验 + 降级 |
| 上下文爆炸 | 三层记忆 + 只保留最近一轮原文 |
| 上下文成本失控 | 模型分级路由 + `llm_usage` 按局统计 |
| 规则变体引发争议 | 规则参数全部走配置，不硬编码 |
| 前端偷看底牌 | 信息裁剪在服务端执行 |
| 日志泄露密钥 | 统一脱敏器 + prompt 默认不落盘 + 启动自检 |
